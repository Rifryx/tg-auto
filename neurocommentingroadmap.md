# Neuro-Commenting — проектный роадмап

## Идея проекта

Эксперимент: софт для автоматизации "живого" обсуждения постов в собственном закрытом Telegram-канале при помощи LLM-персон. При выходе нового поста набор Telegram-аккаунтов (управляемых через Telethon) генерирует и оставляет комментарии в привязанной группе обсуждений, имитируя реальную дискуссию между разными типами подписчиков.

Цель — посмотреть, как LLM-персоны обсуждают контент, и (в перспективе) использовать это, чтобы стимулировать органическую вовлечённость.

**Главная задача проекта (реформулировано):** держать три дополнительных Telegram-аккаунта живыми — не дать Telegram заблокировать их за "подозрительную активность". Нейрокомментинг — это нагрузка поверх, а не самоцель. Поэтому выживаемость аккаунтов вынесена в отдельный приоритетный слой (см. раздел **Account Lifecycle**), который стоит выше кампаний: кампания — потребитель здоровых аккаунтов, а не наоборот.

> **Честная вводная про безопасность.** Сама автоматизация юзер-аккаунтов через Telethon (долгоживущие MTProto-сессии, логин из library, постинг по расписанию) и есть та "подозрительная активность", по сигналам которой Telegram банит. Прогрев и health-монитор снижают риск, но не убирают его — это игра в кошки-мышки, и она против ToS. Отсюда базовое проектное решение: **на этих аккаунтах не должно быть ничего ценного — считаем их расходником.**

## Ключевые решения (уже приняты)

- **Постинг:** реальные юзер-аккаунты через Telethon (не Bot API) — реалистичнее, но требует больше защиты аккаунтов.
- **LLM:** DeepSeek API и/или бесплатный тир Gemini. Провайдер настраивается на уровне кампании.
- **Интерфейс управления:** Telegram Mini App — не отдельный сайт/десктоп-панель.
- **Бэкенд:** FastAPI (Python).
- **Опыт:** переиспользуем паттерны из своего же проекта Herald AMS (мультиаккаунт-поддержка, шифрование сессий, APScheduler).

## Account Lifecycle — приоритетный слой (главная цель)

Выживаемость аккаунтов — отдельный слой над кампаниями. Аккаунт движется по стадиям, а health-монитор — это движок переходов между ними (каждый `HealthEvent` умеет двигать аккаунт по стадиям автоматически).

### Стадии аккаунта (`Account.status`)

1. **`created`** — сессия есть, кампании его ещё не трогают. На этой стадии обязательно:
   - сгенерирован и зафиксирован фингерпринт устройства (см. ниже);
   - привязан выделенный прокси (один прокси = один аккаунт, гео прокси совпадает с гео номера);
   - желательно выставлен 2FA-пароль.
2. **`warming`** — прогрев неделями, не часами. Медленные человекоподобные действия (см. Warming-лог). Никаких сообщений незнакомцам.
3. **`active`** — доступен кампаниям, но под лимитами (частота комментов, флуд-паузы, окна активности).
4. **`limited` / `cooldown`** — при флудвейте/ограничении автопауза и "отдых", а не долбёж. Возврат в `active` после выдержки.
5. **`retired` / `banned`** — вывод из пула, разбор по логам.

### Почему аккаунты "умирают, хотя ничего не делаешь"

Учитываем при проектировании как источники сигналов, которые надо гасить:

- **Номер** — дешёвые виртуалки/VOIP и номера из-под ранее забаненных аккаунтов помечены ещё до первого действия (причина №1 мгновенных банов).
- **Вход через library** — первый логин сразу через Telethon с датацентр-IP; репутация и "возраст" сессии считаются.
- **Фингерпринт устройства** — одинаковые или дефолтные device/app/lang у нескольких аккаунтов = паттерн.
- **Общий IP/подсеть** — несколько сессий с одного адреса банятся кластером.
- **Idle ≠ безопасно** — аккаунт, который просто существует и изредка логинится ботом без человекоподобного поведения, подозрительнее активного; а без логина ~6 месяцев Telegram сам деактивирует (не бан, но потеря).

## Генерация фингерпринта аккаунта

Фингерпринт — часть личности аккаунта. Генерируется **один раз** при создании (стадия `created`) и **никогда не меняется** — смена фингерпринта существующей сессии сама по себе триггер антифрода.

### Поля (хранятся в `Account`)

```
device_model        # напр. "Samsung SM-G991B", "iPhone14,2", "PC 64bit"
system_version      # напр. "Android 13", "iOS 17.2", "Windows 11"
app_version         # версия клиента, согласованная с system_version
lang_code           # язык интерфейса, напр. "ru", "uk"
system_lang_code    # системный язык, напр. "ru-RU"
```

Эти параметры передаются в `TelegramClient(..., device_model=, system_version=, app_version=, lang_code=, system_lang_code=)` при каждом подключении — из сохранённых значений, а не из дефолтов Telethon.

### Правила генерации (согласованность важнее случайности)

- Значения должны быть **взаимно согласованы**: реальная связка device_model ↔ system_version ↔ app_version (не "iPhone" + "Android 13").
- `lang_code` / `system_lang_code` согласованы с гео номера и прокси.
- Черпать из справочника реальных связок (пул популярных моделей + актуальные версии Telegram под платформу), а не собирать строки случайно.
- Разнообразие между аккаунтами: три аккаунта — три разных устройства/платформы, чтобы не выглядеть кластером.
- Фингерпринт сохраняется вместе с сессией (шифруется тем же контуром, что и `.session`).

### Задачи

- [ ] Справочник согласованных связок device/system/app (JSON или таблица в БД).
- [ ] `FingerprintGenerator` — выдаёт согласованный набор, помечает уже занятые связки, чтобы не повторяться внутри пула.
- [ ] Прокидывание фингерпринта во все точки создания `TelegramClient` (логин, воркер, прогрев) из единого источника.
- [ ] Иммутабельность: запрет на изменение фингерпринта после `created` на уровне сервиса.

## Warming — лог и движок прогрева

Прогрев должен быть воспроизводимым и настраиваемым, а не "магией". Вводим отдельную сущность-лог активности прогрева.

### `WarmingActivity` (лог прогрева)

```
WarmingActivity
  - account_id
  - action_type        # subscribe_channel | read_history | reaction |
                       #   view_media | join_group | idle_online | update_profile
  - target             # nullable — на что было направлено (канал/чат/сообщение)
  - timestamp
  - status             # done | failed | skipped
  - meta               # nullable JSON (детали: id канала, эмодзи реакции и т.п.)
```

### Логика прогрева

- Длительность — недели, не часы; срок настраиваемый (стадия `warming` до перехода в `active`).
- Человекоподобные действия с джиттером по времени и в пределах окон активности:
  - подписки на публичные каналы по интересам персоны (постепенно, не пачкой);
  - реальное "чтение" — двигать `read` статус истории;
  - редкие реакции/просмотры медиа;
  - `idle_online` — просто быть онлайн в разумных окнах;
  - редкие правки профиля (не сразу после создания).
- Никаких сообщений незнакомцам на прогреве.
- Каждое действие пишется в `WarmingActivity` → прогрев воспроизводим, настраиваем и разбираем по логам.
- Критерий готовности к `active`: настраиваемый (по сроку и/или по числу успешных действий), без флуд-инцидентов за период.

### Задачи

- [ ] Модель `WarmingActivity` + миграция.
- [ ] Профиль прогрева (набор действий, частоты, окна) — настраивается на уровне аккаунта/персоны.
- [ ] Планировщик прогрева в воркере с джиттером и лимитами.
- [ ] Условие перехода `warming → active`.
- [ ] Отображение хода прогрева в Mini App (таймлайн активности аккаунта).

```

  - status (alive/dead), assigned_account_id

Account
  - session (зашифрована)
  - phone, proxy_id
  - avatar_url, bio, username
  - status: created | warming | active | limited | cooldown | retired | banned
  - persona_id (если используется библиотека персон)
  # --- фингерпринт (иммутабелен после created) ---
  - device_model
  - system_version
  - app_version
  - lang_code
  - system_lang_code
  # --- lifecycle ---
  - warming_started_at, activated_at (nullable)

Persona (библиотека персон)
  - name, avatar_template, bio_template
  - base personality tags (характер, стиль речи)

Campaign
  - name
  - target_channel
  - base_system_prompt
  - llm_provider (deepseek / gemini)
  - active_hours (окно активности, напр. 09:00–23:00)
  - posting_delay_range (мин/макс между комментариями)

CampaignAccount (M2M)
  - campaign_id, account_id
  - override_prompt (nullable — если задан, используется вместо base_system_prompt кампании)

WarmingActivity (лог прогрева)
  - account_id
  - action_type, target (nullable)
  - timestamp, status, meta (nullable JSON)

CommentLog (аудит)
  - account_id, campaign_id, post_id
  - comment_text, timestamp, in_reply_to (для тред-симуляции)
  - status (posted / failed / flagged)

HealthEvent
  - account_id, event_type (flood_wait, spam_block, restricted, proxy_down)
  - timestamp, resolved (bool)
  - triggered_status_change (nullable — в какую стадию перевёл аккаунт)
```

## Функционал v1 (обязательный)

### 1. Прогрев аккаунтов (warming)
- Новый аккаунт не сразу попадает в кампанию — проходит период "естественной" активности: подписки на каналы, чтение, лайки, случайные действия.
- Настраиваемый срок прогрева перед тем, как акк становится доступен для кампаний.
- Каждое действие фиксируется в `WarmingActivity` (см. раздел Warming).

### 2. Health-монитор
- Отслеживание статуса каждого аккаунта: флудвейты, ограничения на отправку сообщений, spam-block.
- **Движок переходов между стадиями** — `HealthEvent` автоматически двигает аккаунт (`active → limited/cooldown → active`, либо `→ banned`).
- Авто-пауза кампании на аккаунте при обнаружении проблемы.
- Ротация/проверка живости прокси, авто-замена при падении.
- Rate-limit governor: глобальные и на-аккаунт лимиты действий в час/сутки с джиттером — главная защита от флудвейтов.
- Алерты в Mini App при проблемах с аккаунтом или прокси.

### 3. Библиотека персон
- Готовые шаблоны персон (имя, био, аватар, характер), чтобы не создавать каждый аккаунт вручную.
- Персона привязывается к аккаунту при создании/прогреве.

### 4. Рандомизация стиля
- Пост-обработка ответа LLM: варьирование длины, наличия эмодзи, опечаток, тона.
- Разный стиль по персонам, чтобы паттерн генерации не был "слишком ровным" и предсказуемым.

### 5. Тред-симуляция
- Персоны реагируют не только на исходный пост, но и друг на друга (и опционально на реальных живых комментаторов).
- Контекст треда накапливается и передаётся в промпт следующей персоне.

### 6. Расписание / окна активности
- Кампания активна только в заданные часы (напр. "тихие часы" ночью отключены).
- Возможность задать разное расписание для разных кампаний/каналов.

### 7. Лог / аудит
- Полная история: кто из аккаунтов, что и когда написал, в рамках какой кампании.
- Возможность разобрать инцидент (бан, странное поведение LLM) по логам (`CommentLog` + `HealthEvent` + `WarmingActivity`).

## Функционал — отложено на будущее (v2+)

- Dry-run / модерация комментариев перед публикацией
- Мульти-канал на одну кампанию/пул аккаунтов
- Метрики эффективности (рост органических реакций после кампании)
- A/B тестирование кампаний/промптов
- Manual override — ручное редактирование коммента от лица персоны

## Архитектура

```
┌─────────────────────┐
│  Telegram Mini App   │  (WebView UI: аккаунты, кампании, персоны, логи, прогрев)
└──────────┬───────────┘
           │ REST (через initData-авторизацию)
┌──────────▼───────────┐
│   FastAPI backend     │  CRUD: /accounts, /campaigns, /personas, /channels
│  (лёгкие операции)    │  Логин-флоу: /accounts/login/start, /confirm
└──────────┬───────────┘
           │ БД / очередь задач
┌──────────▼───────────┐
│   Worker-процесс      │  Отдельный процесс (НЕ в FastAPI event loop):
│  (Telethon-пул)       │  - слушает каналы (NewMessage)
│                       │  - держит пул активных TelegramClient (с фингерпринтом)
│                       │  - гоняет прогрев (warming) и пишет WarmingActivity
│                       │  - гоняет LLM-генерацию по кампаниям
│                       │  - постит с задержками через прокси аккаунта
│                       │  - двигает стадии аккаунта, пишет health-события и лог
└───────────────────────┘
```

**Важно:** FastAPI-процесс и воркер-процесс разделены намеренно — Telethon-клиенты долгоживущие и блокирующие, конкурентный доступ к одному `.session` файлу из разных процессов ломается. Общение между слоями — через БД/очередь (напр. Redis/RQ или polling таблицы задач).

## Стек

- **Backend:** FastAPI (Python)
- **Telegram-аккаунты:** Telethon (фингерпринт передаётся в каждый `TelegramClient`)
- **Frontend:** Telegram Mini App (WebView)
- **LLM:** DeepSeek API (OpenAI-совместимый) и/или Gemini free tier
- **БД:** (не выбрана — вероятно Postgres, учитывая структуру с M2M и логами)
- **Шифрование сессий:** тот же подход, что в Herald AMS (фингерпринт шифруется тем же контуром)
- **Планировщик/очередь задач:** APScheduler или Redis/RQ (уточнить на этапе реализации)

## Приоритет разработки

Раз главная цель — выживаемость аккаунтов, инфраструктура аккаунтов идёт **вперёд** LLM-комментинга:

1. Сессии + шифрование + логин-флоу (2FA/флудвейты).
2. Прокси-привязка + генерация и фиксация фингерпринта.
3. Прогрев (`WarmingActivity`) + движок стадий.
4. Health-монитор + rate-limit governor.
5. И только потом — кампании, LLM-генерация, тред-симуляция, рандомизация стиля.
