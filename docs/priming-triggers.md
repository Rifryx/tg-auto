# MTProto-триггеры прайминга — матрица результатов R&D

Заполняется по результатам прогонов `scripts/priming_rnd/` (см. его
`README.md`). Каждая строка — один кандидат из
`docs/priming-spec.md §5`, подтверждённый живыми тестами на паре
подконтрольных аккаунтов.

**Пока пусто — R&D не проведён.** Матрица ниже — шаблон, который заполняет
оператор после прогонов; отчёты складываются в
`scripts/priming_rnd/reports/`, а сюда попадают сводные выводы.

## Как читать колонки

- **push_seen** — приходит ли пуш у цели на iOS/Android/Web (пометьте
  платформы, где расходится).
- **chat_artifact** — появляется ли в личке видимое сообщение или
  служебная строка. Для прайминга должно быть **нет**.
- **RPC-errors** — типовые ошибки (privacy, deactivated, invalid), с
  которыми надо уметь работать в `TriggerRunner` (см. промпт 2.1).
- **MVP?** — отметить два-три самых надёжных action'а, которые пойдут
  в первый релиз модуля.

## Рекомендация для MVP

Финализируется после прогонов. Ожидаемый порядок предпочтения
(по спеке §5, до подтверждения на живых аккаунтах):

1. `secret_chat_request` — уникальный push, минимум артефактов, но
   часть клиентов может отклонить.
2. `set_ttl_1d` / `set_ttl_off` — рабочая пара для ротации; риск —
   требует непустого диалога.
3. `contact_added` — резерв; вероятно, самый шумный для UX цели.

## Что делать при провале кандидата

- Если push не приходит стабильно — в MVP не берём, но оставляем в
  реестре `worker/priming/trigger.py` за фиче-флагом (для повторного
  R&D после апдейтов Telegram).
- Если у action меняется артефакт в чате в зависимости от режима цели
  (например, secret chat отклонён) — фиксировать `outcome` отдельно и
  прописать в спеку как «cannot_trigger_push».
